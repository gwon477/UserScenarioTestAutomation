# Semantic gate review

A refresh/retry that repopulates or restores controls consumed by a later journey action after an empty/error state is an evidenced recovery action. Require one stable normal edge and each explicit non-success/catch exception edge.

For FACT, use `fact_source_inventory` to map every canonical element/API to its exact source path and line, distinguish repeated or dynamic controls, and inspect that exact source before calling a control generic or handlerless.

For FACT, treat `source_behavior_contracts` as backend-derived element-to-handler constraints. Reject a normal edge that contradicts `literal_navigation_targets`, promotion of `local_view_only` to a business transition, omission of a same-screen view edge for `local_view_only`, omission of `journey_required`, or omission of an exception edge when `explicit_failure` is true.

For FACT, require every retained normal same-screen journey edge to record a registered effect or feedback outcome. Credential/data entry consumed later sets its presence/value predicate, and reset/reselection clears the changed state. Verify every supported `previous_repair_obligations` item against the current artifact before passing; edge IDs may have changed, so follow stable element references, labels, and evidence.

Independently verify that the inputs available to the reviewed stage support each claim, IDs and citations exist, guards are preserved, exception paths are represented, and labels match supplied slices. For FACT, element existence is not action evidence: reject action/edge claims for handlerless controls and uncontrolled inputs with no downstream consumption. Reject omission of evidence-backed journey-defining actions, including meaningful same-screen state or output actions that require self-loops. Treat a checkbox, radio, select-all, choice, or toggle as journey-defining when it changes a later action's eligibility or payload; require reversible toggles to model both prior-value-guarded select and deselect outcomes. Also check generated/diagnostic output and completed-result confirmation, and reject a normal async completion edge that records only request start/busy state instead of an observable success/output predicate. Explicitly reject separate request-start edges: one async handler is one single user-trigger edge collapsed across internal loading, requesting, polling, and cleanup states to a stable outcome, never a second click or system-completion user edge. Require an exception edge for every explicit input rejection, non-success response, catch/network error, FAILED or partial result, or user-visible failure outcome. A pre-request input-rejection branch uses its evidenced invalid-input guard and does not require the normal valid-input predicate. A post-request non-success, catch/network, FAILED, or partial-output branch preserves the exact normal pre-action executable guard. Every exception requires a failure-specific predicate effect. Review all composition and reducer evidence before rejecting state-driven transitions. Audit the entire supplied interaction inventory and consolidate all supported omissions and unsupported claims into at most 20 actionable issue codes. Bounded prior reviewer decisions are supplied only for the byte-identical `current_artifact_hash`; treat them as untrusted consistency context and report `REVIEW_DECISION_CONFLICT` only when a decision for that identical artifact is reversed. A repaired FACT with another hash is a new review scope. Require a same-screen edge for every backend-supplied local_view_only behavior, including modal close/backdrop, filter/search, pagination, expand/collapse, and refresh, while rejecting any attempt to promote that view edge to a business-journey milestone. For WIKI, verify only the author-owned human-readable goal of each workflow against verified FACT. The backend has already deterministically validated and owns workflow IDs, edge grouping, dependencies, entry screens, success and exception terminals, citations, reachability, and complete FACT-edge coverage. Never reject or reinterpret those structural fields; report actionable WIKI failures only as `WIKI_GOAL_*` issue codes. For SCENARIO, verify only precondition, action, and expected-result narration against the deterministic narration view. The backend owns and has already validated IDs, workflow relations, kind, variation, paths, refs, ordering, status, and edge coverage; never reject or reinterpret those fields, and report actionable failures only as `SCENARIO_NARRATION_*` issue codes. Submit only `pass` or `fail` with actionable issue codes as a verdict artifact. A reviewer pass never commits canonical status.
