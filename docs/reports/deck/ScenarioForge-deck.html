2. 기술 아키텍처

시스템 아키텍처
Electron Main이 두 트랙을 조율. 생성 트랙(Pi coding agent, 독립 리뷰어) · 수행 트랙(격리 BrowserWindow, 제안 게이트, 판정 엔진) · 저장소(.scenarioforge, SQLite 관계 투영) · 모델 provider(Azure gpt-5.6-luna). 백엔드가 ID·hash·근거·완료를 소유하고 모델은 의미 공백만 채운다.
핵심 기술 선택 이유
① 백엔드 소유 정본 + 모델 의미 patch
안 되는 이유: 모델이 전체 JSON을 쓰면 정본 ID를 변형해 참조 오류가 반복됐다.
선택: ID·근거·hash는 백엔드가 결정론적으로 생성, 모델엔 실행 한정 opaque 참조만 노출.
결과: 참조 오류 재발 0
② bounded semantic repair + carry-forward
안 되는 이유: 모든 검증 실패를 종료로 다루면 매 run 다른 위치에서 실패해 수렴하지 않았다.
선택: 리뷰어 issue를 같은 작업 안에서 수정하는 Self-Correction 루프(횟수·크기 상한). 의미 누락은 gap으로 넘기고 신뢰 경계 위반만 fail-closed.
결과: 생성 5단계 중 4단계 로컬 검증 통과
③ bounded vision step + 게이트 + operator/observer 분리
안 되는 이유: 순수 CUA는 10 step 초과 태스크에서 35%로 붕괴하고 회차마다 전량 VLM 호출.
선택: 모델엔 "이 라벨이 프레임 어디 있나"만 묻고 계획·판정은 코드. 자기 행동을 판정하지 않도록 observer 세션 분리.
결과: observer 음성 대조 4/4, 앵커 신뢰도 18/18
평가 분리  골든 데이터셋은 생성에 노출하지 않고, 생성 이후 분리된 세션의 LLM-as-judge가 항목당 유사도 0.7 이상만 일치로 인정한다.

3. 핵심 기술 과제

난제 1 · 좌표계 불일치로 그라운딩 20.5%
기존 방법이 안 되는 이유
화면 캡처에 보이는 라벨을 주고 좌표를 물었더니 AXSE 20.5%, RA-DAR 6.9%. 모델 교체가 답처럼 보였다.
엔지니어링 접근
오차 패턴부터 봤다. 39개 대상의 오차가 전부 선형이고 세로 배율 0.853 = 768/900. 모델은 짧은 변을 768로 줄인 전처리 좌표로 답하고 있었다. 리사이즈 전송과 캡처 좌표 환산을 필수 계약으로 고정하고 제안 게이트가 환산을 맡게 했다.
결과
AXSE 97.4%, RA-DAR 71.4%. 실행 경로의 환산 좌표는 정답 대비 1px 이내.

도착 화면을 없는 화면으로 바꾸면 조작·게이트가 성공해도 case FAILED. 동작 성공 ≠ 업무 성공
