# ScenarioForge 발표 대본

총 10분. 표지 15초, 개요 2분, 아키텍처 4분, 기술 과제 3분 30초, 여유 15초. 15분을 넘기면 초과분은 평가에서 제외되므로 아키텍처 장에서 시간을 확인한다.

## 표지 (15초)

"소스코드 하나로 사용자 여정 시나리오를 만들고 실제 화면에서 실행하는 ScenarioForge입니다. 부제의 숫자 세 개는 전부 실측값이고, 마지막 장에서 근거를 보여드리겠습니다."

## 1. 프로젝트 개요 (2분)

문제 (30초). "브라운필드 웹 시스템의 E2E 테스트는 사람이 화면을 보며 시나리오를 쓰고, 다시 손으로 실행하며 캡처합니다. 기존 자동 생성 도구는 소스의 전이 65개를 전부 덮어 coverage 100%를 기록했지만, 로그인에서 로그아웃까지 이어지는 시나리오는 하나도 없었습니다. 많이 만드는 것과 따라 할 수 있는 것은 다릅니다."

흐름 (45초). "두 개의 엔진입니다. 생성은 스캐너가 소스 범위와 정본 ID를 먼저 정하고, Pi author가 소스 조사부터 시나리오 케이스까지 5단계를 한 번에 하나씩 씁니다. 리뷰어가 검토하고, 골든 평가자는 생성이 끝난 뒤에만 봅니다. 수행은 컴파일러가 step을 만들고, 모델은 '버튼이 어디 있나'와 '화면에 이 문구가 보이나'만 답하며, 클릭 여부는 게이트가, 합격 여부는 판정 엔진이 정합니다."

성과 (30초). "골든 대비 업무 분류 6/6, 업무흐름 10/10, 사용자 여정 2/2로 100%. 실제 앱 두 개에서 3 step씩 전부 통과. 화면 요소 그라운딩은 20.5%에서 97.4%가 됐습니다."

메시지 (15초). "기억하실 한 문장입니다. 소스코드만으로 사용자가 끝까지 따라 할 수 있는 여정 시나리오를 만들고, 그것을 실제 화면에서 실행해 증거까지 남깁니다."

## 2. 기술 아키텍처 (4분, 시간 확인 지점)

그림 (90초). "왼쪽이 생성 트랙, 오른쪽이 수행 트랙, 아래가 프로젝트 저장소입니다. 강조된 두 상자, 리뷰어와 제안 게이트가 모델 출력을 검증하는 코드 게이트입니다. Renderer에는 Node 권한이 없고 허용된 IPC만 지납니다. 모델 provider는 Electron Main만 호출합니다. 원칙은 하나입니다. ID, hash, 근거, 완료 판정처럼 틀리면 안 되는 것은 백엔드가 소유하고, 모델은 의미 공백만 채웁니다."

선택 ① (40초). "처음엔 모델이 산출물 JSON 전체를 썼습니다. 긴 정본 ID를 옮겨 적다 변형해 참조 검증에서 계속 실패했습니다. 그래서 백엔드가 골격을 결정론적으로 만들고, 모델에는 실행 한정 참조만 보여주고 의미 patch만 받습니다. 이후 참조 오류 재발은 0입니다."

선택 ② (40초). "모든 검증 실패를 종료로 다루면 매 run 다른 위치에서 실패해 수렴하지 않았습니다. 리뷰어 issue를 같은 작업 안에서 고치는 Self-Correction 루프를 두되 횟수와 크기에 상한을 걸었습니다. 의미 누락은 gap 목록으로 다음 단계에 넘기고, ID·hash·범위·secret 위반만 즉시 종료합니다. 이 구조로 생성 5단계 중 4단계가 로컬 검증을 통과했습니다."

선택 ③ (40초). "순수 CUA를 쓰지 않은 이유는 두 가지입니다. 공개 실측에서 10 step 넘는 태스크 성공률이 35%로 무너지고, 회차마다 전량 VLM 호출이라 비용이 누적됩니다. 그래서 계획은 컴파일러가, 판정은 코드가 갖고 모델은 위치 제안만 합니다. 모델이 자기 행동을 판정하지 않도록 observer 세션을 분리했고, 없는 문구를 물었을 때 되뇌지 않는지 4/4, 앵커 신뢰도 18/18로 확인했습니다."

평가 분리 (20초). "골든 데이터셋은 생성에 노출하지 않습니다. 생성이 끝난 뒤 분리된 세션의 LLM-as-judge가 항목당 유사도 0.7 이상만 일치로 인정합니다."

## 3. 핵심 기술 과제 (3분 30초)

난제 1 (110초). "그라운딩 적중률이 AXSE 20.5%, RA-DAR 6.9%였습니다. 모델 교체가 답처럼 보였습니다. 대신 오차 패턴을 봤습니다. 39개 대상의 오차가 전부 좌상향 선형이었고 세로 배율이 0.853, 즉 768/900이었습니다. 모델은 짧은 변을 768로 줄인 전처리 이미지 좌표로 답하고 있었던 겁니다. 리사이즈 전송과 좌표 환산을 필수 계약으로 고정하고 게이트가 환산을 맡게 하자 AXSE 97.4%, RA-DAR 71.4%가 됐고, 실행 경로의 환산 좌표는 정답 대비 1px 이내입니다. RA-DAR에 남은 실패 8건은 전부 화면에 글자가 없는 아이콘이나 잘린 날짜 셀 같은 대상 서술 문제였습니다."

난제 2 (35초). "환각은 스키마로 막히지 않았습니다. ID 변형, 핸들러 없는 버튼을 동작으로 생성, guard 누락이 매 run 다른 위치에서 재발했습니다. 소유권 경계와 repair loop로 참조 오류 재발 0, recall 100%입니다."

난제 3 (35초). "429가 나면 Pi 내부 4회와 실행기 3회 재시도가 겹쳐 최대 12회 호출로 증폭됐고, 프롬프트 중복으로 요청당 약 104K 토큰까지 커졌습니다. 재시도 소유권을 실행기 하나로 합치고 중복을 제거해 같은 입력이 rate limit 없이 완료됩니다."

로그 증거 (20초). "고수준 로그 두 줄입니다. 단계 handoff에서 gap 3건을 허용 소스 6개 재읽기로 전부 해소하고 evidence 22건이 정합했습니다. 게이트 재생 64건에서 옳은 제안 53 통과, 틀린 제안 1 통과, 과차단 5건은 정규화 수정 후 0입니다."

배운 것 (20초). "미달 두 개, 시나리오 성공 recall 37.5%와 RA-DAR 71.4%는 모델 성능이 아니라 AI에게 시키는 범위의 문제로 특정됐습니다. 전이 원장과 경로 컴파일러 연결로 80%, 라벨 가시성 필드로 90%가 단기 경로입니다. 질문 받겠습니다."

## 예상 질문과 답의 근거

- 정답은 누가 만들었나. AXSE 소스를 사람이 직접 읽어 수작업 구축, 확정·추론 구분 표시 (골든 데이터셋 문서).
- 0.7은 왜인가. 채점 규칙의 정의값. 0.6이면 46.9%, 0.8이면 15.6%로 민감도가 커서 수치를 같이 공개 (KPI 절 합격선 표).
- 37.5%는 왜 못 올렸나. 보정 계획이 넓은 gap을 종류당 1건으로만 변환해 케이스 4 → 8건. 다음 단계는 백엔드가 경로를 열거 (미달성 분석 표).
- 모델을 바꾸면 되지 않나. 좌표계 계약이 없으면 정확한 모델도 20% 이하로 보인다. 계약을 고정했으므로 모델 교체와 무관 (PROBE-01/02).
- 시간이 남으면 뺄 것 없이 진행, 부족하면 난제 3을 한 문장으로 줄인다.
